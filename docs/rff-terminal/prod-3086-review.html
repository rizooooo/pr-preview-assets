Summary

Rate-limits the two Terminal endpoints the RFF extension actually calls for specific-date availability (British Airways v2's dedicated route, and the generic/Iberia route). Over the agreed thresholds, both return a sanitized 429 instead of hitting the database. Backed by Upstash (HTTP-based Redis), keyed primarily by account identity with a hashed-IP fallback, and fails open on any store error so a Redis problem can never become a Terminal outage.

Ships today as a no-op: the Redis credentials are deliberately empty until Infra confirms the provisioning approach (Upstash vs. VPC-attached ElastiCache) — that's the one real blocker left, and it's an infra decision, not a code one.

Open items that need a decision, not a code review

1. Infra — provisioning

Upstash (HTTP-based Redis) vs. VPC-attached ElastiCache. Terminal's Lambdas have no VPC attachment today, so ElastiCache would be a first. Recommendation on file is Upstash; needs their sign-off either way. The PR is a safe no-op until this resolves — nothing turns on by itself.

2. A stakeholder's Slack correction — consent-based keying ✓ resolved

"To be clear — the REDIS cache approach is only for Users that tell us not to log/store their User data to their User profile — i.e. they don't give us permission to create PII data. If they give us permission, we keep the current approach, and we don't anonymise their data." Product stakeholder, internal Slack, post-call

Checked what this actually means in Terminal's code before assuming a gap: the account-identified key is already the literal, unhashed userId — only the no-token IP fallback gets hashed. So "account-linked, not anonymized" is already true today for every authenticated caller, which is what the stakeholder's message was actually asking for.

Resolution: every caller — consent granted or not — stays on the ephemeral Redis counter; no persisted-DB counter will be built. The written acceptance criteria on both this ticket and the parent initiative are blanket Redis/ephemeral with no consent carve-out — the carve-out only ever existed in the Slack comment above, which was never reconciled back into either AC. Decided and posted to the ticket's own comments; a persisted-DB path remains available as separately-scoped future work if the team ever asks for it against the written requirements, but nothing is being built for it now.

Same resolution applies on the Feed side (14zpb0j3pbb) — most of Feed's ingestion rate limiting already shipped in October/November, ahead of this ticket.
